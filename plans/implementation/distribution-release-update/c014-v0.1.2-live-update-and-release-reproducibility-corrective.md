## 1. Objective

Use v0.1.2 as a deliberately small qualification release to close the two material release-process gaps left after Phase 10:

1. prove the **real self-update commit path** by updating an isolated, self-managed public v0.1.1 installation to public v0.1.2 through the actual crates.io version authority and GitHub release assets; and
2. make release bytes materially more reproducible by pinning the release Rust toolchain to an exact version and requiring crates.io publication from the exact tagged source commit.

C014 is not a new feature milestone. Product behavior should remain 0.1.1-compatible except for any narrowly required release/update corrective discovered while producing the evidence.

## 2. Why the previous closure was partial

M010D records one requirement as closed partial: v0.1.1 is both the newest published version and the first release containing a working updater, so there was no possible public older-working-updater -> newer-release transaction to execute.

Fixture tests prove Eggup staging, verification, destination ownership revalidation, commit, and recovery mechanics, and C011 proves the production transport reaches the live registry. They do not prove the released v0.1.1 binary can fetch, verify, and replace itself with a newer public cargo-cleanme release.

M010D also records two release-process weaknesses:

- `release/eggpack/pack.toml` pins Rust as `stable`, so rebuilding the same tag at a later date may use a different compiler and produce different bytes;
- v0.1.1 was published to crates.io from `d478257`, not directly from tag commit `95bb38e`. The package payload was shown equivalent except for `.cargo_vcs_info.json`, because intervening changes were plans-only, but the release process should not depend on proving a harmless mismatch after the fact.

C014 closes these gaps instead of normalizing them as permanent process exceptions.

## 3. Invariants

- Preserve the existing cleanup safety boundary completely.
- Preserve C011's production updater transport and no-downgrade rule unless new evidence proves a defect.
- Do not reintroduce `eggup-curl` as a fallback.
- A Cargo-managed install remains manager-owned and must not be overwritten by self-update.
- A self-managed install may be replaced only after the existing Eggup ownership, digest, candidate-identity, lock, and commit checks succeed.
- GitHub release assets must be published and downloadable before crates.io advertises the new stable version.
- The v0.1.2 crate must be published from the exact v0.1.2 tag commit, not from a later documentation/planning commit.
- Required release targets must use one explicitly recorded exact Rust release toolchain; `stable` is not sufficient release input.
- MSRV remains Rust 1.89. The exact release-builder version is a separate producer fact and must not be described as a new MSRV.
- Never rebuild or replace qualified v0.1.2 release assets after publication.
- SHA-256 remains integrity evidence, not authenticity/signing.

## 4. Scope and non-goals

In scope:

- exact release Rust toolchain pinning;
- release-contract/check tooling that rejects an unpinned release toolchain;
- exact tag/source identity checks for crate publication;
- v0.1.2 version/changelog/release preparation;
- staged-draft qualification under the existing Eggpack contract;
- public v0.1.2 GitHub release and crates.io publication;
- a real v0.1.1 -> v0.1.2 self-update commit rehearsal;
- a real Cargo-managed refusal/remediation rehearsal;
- cross-platform post-publication smoke isolated from user/system state;
- closure evidence and release-process documentation.

Out of scope unless a defect is found:

- new cleanup features;
- new updater features;
- switching update transports;
- signing/notarization;
- new release targets;
- Homebrew/other package managers;
- automatic background updates;
- publishing any Eggup/Eggpack crate.

## 5. Work package A — Pin the release toolchain

Select one exact stable Rust release for v0.1.2 after verifying it:

- builds/tests cargo-cleanme;
- supports all five required release targets through the current Eggpack build strategies;
- works with pinned cargo-zigbuild 0.23.3 / Zig 0.14.1 on the Linux targets;
- does not change the declared Rust 1.89 MSRV.

Replace every `rust = "stable"` in `release/eggpack/pack.toml` with the same exact version unless target-specific evidence genuinely requires otherwise.

Regenerate/check the Eggpack release workflow.

Extend `scripts/check-release-contract.py` or another precise release check so a future required target using `stable`/floating Rust fails before staging.

Closure evidence must record `rustc -Vv` and the exact configured version.

Do not guess the toolchain version in planning; implementation chooses and records the exact qualified release.

## 6. Work package B — Enforce release source identity

Add a bounded source-identity check for publication.

At minimum it must prove:

- working tree clean;
- requested release tag is `v<Cargo.toml package.version>`;
- the tag resolves to the current HEAD;
- package/publish dry-run is run at that exact tagged commit;
- actual `cargo publish --locked` is executed from that exact tagged commit;
- release manifest source revision matches the same commit.

This may be implemented as a dedicated script or as a strict mode in `release-check.sh`, but it must be machine-checkable rather than prose-only.

Update `docs/RELEASING.md` so the operator sequence cannot repeat the v0.1.1 "tagged bytes, later publish commit" deviation.

After tagging v0.1.2, planning/closure documentation may continue on `main`, but crates.io publication must still be performed from a detached checkout/worktree of the exact tag.

## 7. Work package C — Prepare the minimal v0.1.2 release

Before tagging:

- close C013;
- bump package version to 0.1.2;
- update Cargo.lock and CHANGELOG;
- update any generated docs whose version text is material;
- keep feature changes out unless required by an independently registered corrective;
- run the complete clean-tree release gate.

Required local gate:

~~~text
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-targets --all-features
cargo +1.89 check --locked --all-targets
cargo +1.89 test --locked --all-targets
python3 scripts/release-benchmark.py --check
cargo run --quiet --features dev-tools --bin generate-docs -- --check
python3 scripts/gen-release-workflow-shape.py --check

python3 scripts/check-installer-contract.py
python3 packaging/tests/test_installers.py
cargo package --locked
cargo publish --locked --dry-run
bash scripts/release-check.sh
~~~

Hosted CI and release drift guard must both be green on the release commit.

## 8. Work package D — Stage and qualify exact v0.1.2 bytes

Follow the established order:

1. tag the exact release commit `v0.1.2`;
2. dispatch the Eggpack candidate-build workflow at that tag;
3. require all five build/qualify/validate target lanes and aggregate/stage gates green;
4. validate the staged draft before publication;
5. verify exactly the contracted inventory;
6. verify every sidecar digest against the actual served draft bytes;
7. verify `release-manifest.json` binds v0.1.2 to the exact tag source revision;
8. verify both Linux artifacts retain the qualified glibc 2.17 floor;
9. run the real installer against the staged release candidate where the existing validation tooling permits.

Any byte-changing rerun invalidates prior qualification.

## 9. Work package E — Publish in source-safe order

Preserve the successful M010D ordering:

1. publish the already-qualified GitHub draft;
2. from the exact v0.1.2 tag checkout/worktree, run the source-identity check;
3. publish `cargo-cleanme 0.1.2` to crates.io;
4. verify registry checksum/version/non-yanked state;
5. perform registry-only external install smoke.

If publication source identity fails, stop. Do not "prove equivalence later" as the normal path.

## 10. Work package F — Real updater commit-path rehearsal

After both authorities expose v0.1.2, exercise the **released v0.1.1 updater**, not a newly built copy.

For a self-managed installation:

1. create an isolated temporary install directory/home;
2. install exact public v0.1.1 using the published installer or exact v0.1.1 release asset;
3. record the v0.1.1 binary digest and `--version`;
4. run `cargo-cleanme update` **without** `--dry-run`;
5. require success;
6. require `cargo-cleanme --version` == `0.1.2`;
7. fetch the public v0.1.2 sidecar and require the installed binary digest equals the published v0.1.2 asset digest exactly;
8. verify no unexpected backup/staging residue remains outside Eggup's documented transaction/recovery semantics;
9. run `update --dry-run` again and require AlreadyCurrent.

For a Cargo-managed installation:

1. install exact public v0.1.1 into an isolated Cargo home/root;
2. run its `update`;
3. require refusal as `cargo_managed`;
4. require the remediation command names v0.1.2;
5. require the managed binary digest/version remains v0.1.1 after refusal.

No system/global installation may be mutated by this rehearsal.

## 11. Work package G — Make live smoke repeatable across supported platforms

Add a manually dispatched post-release smoke workflow or equivalent repeatable harness that performs Work Package F in isolated state against public releases.

Required coverage should match the five release targets when the existing release runner matrix can execute them:

- aarch64 macOS;
- aarch64 Linux;
- x86_64 macOS;
- x86_64 Windows;
- x86_64 Linux.

The runner/target mapping must derive from the existing release contract/build bindings or be mechanically checked against them. Do not create an unguarded second target matrix.

This workflow must:

- have no publication credentials;
- mutate only temporary per-job directories;
- use public HTTPS/registry endpoints;
- verify the final binary digest against the public sidecar;
- make network failures visible as failures, not skips/passes;
- be manually triggered for release qualification rather than run on every push.

If all five target runners are not operationally available for this smoke, C014 may close only with explicit platform evidence explaining the gap and a decision whether fixture + OS-family live evidence is sufficient. Do not silently claim five-target live update coverage.

## 12. Failure, rollback, and immutable-version semantics

Because the real commit rehearsal occurs after crates.io publication, failure handling must be explicit.

If v0.1.2 publishes but the live self-update transaction exposes a material defect:

- do not republish different bytes as 0.1.2;
- classify the defect immediately;
- yank the crates.io version if leaving it installable is unsafe/misleading;
- annotate or withdraw the GitHub release as appropriate without rewriting tag history;
- author/register a new corrective and release a new patch version after repair.

Do not call C014 closed merely because publication succeeded.

## 13. Compatibility/configuration effects

- Application configuration is unchanged.
- Cleanup/selective-cleanup behavior is unchanged.
- MSRV remains Rust 1.89.
- Release producer configuration changes from floating Rust `stable` to one exact Rust release.
- v0.1.2 is intended as a release/reliability patch, not a feature change.
- Existing v0.1.0/v0.1.1 releases and historical closure records remain untouched.

## 14. Required tests

In addition to existing suites:

- release-contract test rejects `rust = "stable"` on required targets;
- release-contract test rejects mismatched release-builder Rust versions if uniformity is the chosen contract;
- source-identity checker rejects:
  - dirty tree,

- post-release Cargo-managed smoke proves refusal and no mutation;

Tests around the source-identity helper should use temporary Git repositories/fixtures where practical instead of mutating the real repository.

## 16. Acceptance criteria

C014 closes only when:

- C013 is closed;
- all required `pack.toml` Rust toolchains are exact, not floating `stable`;
- the release contract mechanically enforces the chosen exact-toolchain rule;
- v0.1.2 is tagged from an exact source commit and Eggpack stages qualified bytes from that commit;
- the GitHub release is public with the exact qualified inventory;
- crates.io 0.1.2 is published from the exact v0.1.2 tag commit;
- registry-only installation succeeds;
- a released self-managed v0.1.1 binary performs a real networked update to v0.1.2 and the installed digest equals the public v0.1.2 asset;
- a released Cargo-managed v0.1.1 installation refuses self-update without mutation and gives correct remediation;
- repeatable live smoke is recorded on the supported platform matrix to the extent claimed;
- normal Stable/MSRV/platform CI and release drift guard are green;
- no medium-or-higher release/update finding remains.

## 17. Stop conditions

Stop publication or closure if:

- exact Rust pinning cannot build/qualify a required target;
- generated Eggpack workflow drifts from the contract;
- source tag/version/revision identity is inconsistent;
- the crate cannot be published from the exact tag commit;
- staged bytes change after qualification;
- the v0.1.1 updater cannot perform the real v0.1.2 commit;
- installed bytes differ from the public digest;
- Cargo-managed ownership is mutated;
- Windows running-image replacement fails in the live supported path;
- the live smoke requires privileged/system mutation.

A stop after immutable publication requires a new corrective/version; never rewrite v0.1.2 bytes.

## 18. Closure evidence

Record:

- implementation and release commits;
- exact v0.1.2 tag SHA;
- exact release Rust version and `rustc -Vv`;
- Eggpack pin/workflow run and all target results;
- release asset inventory and SHA-256 values;
- release-manifest source binding;
- crates.io package checksum and proof publication ran at the tag SHA;
- registry-only install evidence;
- self-managed v0.1.1 -> v0.1.2 live-update logs and pre/post digests;
- Cargo-managed refusal/remediation evidence;
- post-release smoke workflow run IDs by target;
- release benchmark/binary-size/dependency baseline;
- unresolved findings by severity;
- disposition.

C014 is the corrective that turns the updater's remaining fixture-only commit proof into real released evidence and removes floating compiler/source-identity ambiguity from future releases.
