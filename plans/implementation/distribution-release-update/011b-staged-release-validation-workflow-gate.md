# M011B — Staged Release Validation Workflow Gate

Status: closed (conditionally — hosted evidence pending a real staged draft)

Closure record: `plans/closure/distribution-release-update/m011b-status.md`

Repository baseline: `c3feae01fe5b684826b77b4d32afcb2e3bd4e3d0`

Source roadmap: Phase 11 — hardening, release trust, and qualification automation

Subsystem roadmap: `plans/subsystems/distribution-release-update-roadmap.md`

Primary class: release-process hardening

Dependencies:

- interface dependency on the existing Eggpack candidate-build workflow name and exact-tag/source contract;
- operational closure requires a real future staged draft.

## 1. Objective

Wire `scripts/validate-staged-release.py` into hosted release qualification so the repository no longer depends on an operator remembering to run the sole end-to-end "staged bytes == qualified bytes" validator.

Do this without hand-editing `.github/workflows/release-binaries.yml`, which is generated by Eggpack and protected by a drift gate.

The product-owned solution is a separate least-privilege validation workflow that subscribes to completion of the Eggpack candidate-build workflow, binds itself back to the exact source/tag, downloads the draft, and executes the existing validator before human publication.

## 2. Current evidence

At the baseline:

- `validate-staged-release.py` checks exact inventory, served-byte SHA-256, release-manifest agreement, contract agreement, static Linux ABI evidence, and a real installer run.
- it has repeatedly caught/prevented release-process defects when run manually;
- architecture review records it as "wired into nowhere";
- the Eggpack workflow stages a draft only after all five target build/qualify/consumer/aggregate gates pass;
- only its `stage` job has `contents: write`;
- manually changing that generated workflow would fail `eggpack ci check`.

## 3. Invariants

- Eggpack remains producer authority for candidate build, qualification, aggregation, and draft staging.
- cargo-cleanme owns this product-specific validation layer.
- The validation workflow has no publication capability and no `contents: write`.
- It may read the private draft using the repository-scoped `GITHUB_TOKEN`; no PAT or long-lived credential.
- It must execute only for a trusted exact-tag Eggpack release run, never arbitrary PR/fork artifacts.
- It must independently re-bind tag, version, and source SHA before trusting the draft.
- A missing draft, missing asset, download failure, ABI measurement failure, or installer failure is red, not skipped.
- Publication remains a human action after both Eggpack staging and this validation are green.
- The validation script remains reusable locally; the workflow is an enforcement point, not a reimplementation.

## 4. Work package A — Add the hosted staged-validation workflow

Add a product-owned workflow, e.g. `.github/workflows/validate-staged-release.yml`, with:

- `workflow_run` on `Eggpack candidate builds`, type `completed`;
- a manual `workflow_dispatch` fallback for recovery/re-run, taking an exact tag and optionally a source workflow-run id;
- `contents: read` only;
- bounded timeout;
- pinned actions by full commit SHA.

For automatic runs:

- require `github.event.workflow_run.event == 'workflow_dispatch'`;
- require the upstream conclusion is success;
- checkout the upstream `head_sha`, not default-branch source;
- derive the package version from that checkout and construct the exact `vX.Y.Z` tag;
- prove the tag resolves to the same upstream head SHA using the existing release-identity logic;
- authenticate `gh` only with the built-in token needed to read the draft;
- run `python3 scripts/validate-staged-release.py --tag <exact-tag>`.

Do not execute code downloaded from workflow artifacts. The validator and policy come from the exact trusted tag checkout.

## 5. Work package B — Make the workflow's premises self-checking

Add a contract checker or extend `check-release-contract.py` so normal CI proves the staged-validation workflow:

- names the Eggpack workflow exactly;
- accepts only `workflow_run` completed plus bounded manual dispatch;
- rejects push/pull_request/schedule triggers;
- has no write permissions or publication commands;
- binds checkout to upstream `head_sha`;
- requires upstream manual-dispatch event and successful conclusion;
- invokes `check-release-identity.py` and `validate-staged-release.py`;
- does not inline/reimplement staged validation.

The checker must have `--self-test` premise negatives for each critical guard. Wire it into normal CI and `release-check.sh`.

## 6. Work package C — Publication gate semantics

Update `docs/RELEASING.md` so publication requires:

1. Eggpack candidate build/stage workflow green;
2. staged-release validation workflow green for the same tag/source SHA;
3. human inspection;
4. then publication.

Do not make the validation workflow publish the draft. A compromised or buggy validation job must not hold publication authority.

If the validation workflow runs late or GitHub has an outage, the release waits; there is no bypass that converts "unavailable" into "passed".

## 7. Work package D — Evidence handoff

The workflow should emit a small validation summary artifact or job summary containing:

- exact tag and source SHA;
- upstream Eggpack run id;
- staged release id if available;
- inventory count;
- validator result;
- measured Linux glibc floors;
- installer qualification result.

Do not copy release binaries into a second long-lived artifact unless needed; the draft is the authority being validated.

## 8. Failure and rerun semantics

- Upstream Eggpack failure: no automatic validation claim.
- Upstream success but no draft: validation fails.
- Validation failure: draft remains draft and publication is blocked.
- Manual rerun must bind to the exact tag/source and cannot validate "latest".
- A rerun after draft bytes change must re-download/revalidate all bytes; cached prior success is not sufficient.
- Once a release is public/immutable, use M011A/M011C verification rather than pretending staged validation is still pre-publication evidence.

## 9. Required tests

- workflow contract checker good fixture;
- wrong upstream workflow name;
- push/pull/schedule trigger;
- `contents: write`;
- checkout of default branch instead of upstream SHA;
- missing upstream event/conclusion guard;
- missing exact release-identity check;
- missing staged validator invocation;
- a validator failure propagates nonzero.

Retain the existing validator's real installer premise checks.

## 10. Verification

~~~text
python3 scripts/check-release-contract.py
python3 scripts/check-release-contract.py --self-test
# or the dedicated new workflow checker and its --self-test
bash scripts/release-check.sh
~~~

Hosted closure additionally requires a real Eggpack draft run followed automatically by this workflow and a green staged validator against that draft.

## 11. Compatibility

No user-visible CLI/config behavior changes.

No Eggpack source change is required for this first implementation because the workflow observes the generated pipeline rather than modifying it.

If GitHub cannot provide a safe source/tag binding through `workflow_run`, stop rather than hand-edit Eggpack output; at that point an Eggpack post-stage-validation hook becomes the correct upstream dependency.

## 12. Acceptance criteria

M011B closes only when:

- staged validation is an actual hosted workflow enforcement point rather than a documented manual command;
- the workflow cannot execute for arbitrary PR/fork runs;
- exact upstream head/tag/version identity is re-proven;
- it has read-only permissions and no publication commands;
- a real future Eggpack draft automatically triggers it;
- the existing validator passes against the actual staged bytes;
- failure leaves the release draft unpublished;
- normal CI/release-check statically guards the workflow's critical premises;
- docs make a matching green validation run a publication prerequisite.

## 13. Stop conditions

Stop and register an Eggpack upstream plan if:

- safe automatic triggering cannot recover/bind the exact release tag from the trusted upstream run;
- validating the draft requires write permissions;
- the only robust solution is to inject product-specific steps into generated Eggpack YAML;
- Eggpack adds a native post-stage validator seam during implementation.

Do not bypass the generated-workflow drift contract.

## 14. Closure evidence

Record:

- real Eggpack run id and source/tag;
- automatic staged-validation run id;
